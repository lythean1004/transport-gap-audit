## [A] 드리프트 분포 정밀 재산출 (1차 오판 항목)
- called_at_kst 와 slot_hhmm 기준시각의 차이(초)를 전 행에 대해 계산.
- 출력: n, mean, std, min, p25, p50, p75, **p90, p95, p99**, max.
- **드리프트 상위 20건**을 표로 전량 출력
  (obs_date, slot_hhmm, called_at_kst, drift_sec, outcome, retry_count).
- 구간별 히스토그램 건수: 0~2 / 2~5 / 5~10 / 10~30 / 30~60 / 60~300 / 300초 초과.
- retry_count>0 행을 제외한 "정규 호출"만으로 위 통계를 **한 번 더** 산출해
  두 버전을 나란히 제시한다.
- 검증 명제: "정규 호출이 전수 1~4초 이내"가 참인지 거짓인지
  p90/p95/max 값을 근거로 **명시적으로 판정**한다.

## [B] TRUNCATED / 응답 완전성 검증 (1차 미검증 항목)
각 raw JSON에 대해 아래를 전수 파싱한다.
- response.header.resultCode, resultMsg → **값별 분포표** 출력
  (00 이외 코드가 있으면 해당 행 전량 출력)
- response.body.totalCount vs 실제 items 길이 → **불일치 건 전량 출력**
- items 길이 vs 원장 item_count → 불일치 건 전량 출력
- numOfRows, pageNo 필드가 있으면 값 분포 출력 (페이지네이션 절단 탐지)
- **파일 크기(byte) 분포**: min/p50/p90/max 및 3500 byte 이상 파일 목록
  (활용가이드상 최대 메시지 4000 byte 제약에 근접했는지 확인 목적)
- item 하나의 nodenm 샘플 출력 (한글 인코딩 확인)
- 결론: TRUNCATED 항목을 PASS / FAIL / UNVERIFIED 중 하나로 판정하고 근거를 적는다.

## [C] item_count 통계 재산출 (1차 오염 항목)
- 1차는 api_error 행을 포함해 계산했다. 아래 3가지 모집단으로 각각 산출:
  (1) 전체 192행  (2) outcome이 ok_* 인 행만  (3) ok_with_items 행만
- 각 모집단에 대해 전체 / 오전(0700-0855) / 오후(1700-1855) 로 나눠
  n, mean, median, std, min, max 를 표로 출력.
- 오전-오후 평균 차이를 모집단별로 제시하고, 1차 보고값(오전 25.68 / 오후 23.35)이
  어느 모집단 기준이었는지 역산해 명시한다.
- item_count==0 인 행 전량 출력 (obs_date, slot_hhmm, outcome, result_code, result_msg).

## [D] ok_empty 2건 원인 판별 (최우선)
- outcome=='ok_empty' 인 행의 raw_path JSON을 **원문 그대로 전량 덤프**한다
  (serviceKey 치환 후).
- header.resultCode / resultMsg, body.totalCount, items 존재 여부를 각각 적시.
- 판정 기준을 코드에 명시:
  * resultCode가 정상(00)이고 totalCount==0 → "실제 배차 공백 가능성"
  * resultCode가 NODATA류이거나 body 구조가 다름 → "API 아티팩트, 결측 처리 대상"
- 두 건 각각에 대해 위 둘 중 어디에 해당하는지 판정한다. 애매하면 "확인불가".
- 참고: 두 건 모두 저녁 피크 시간대이며, 해당 정류소는 상시 13개 노선이 관측된다.
